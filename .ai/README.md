# .ai — Agent-Neutral Rules, Skills & Connectors

This directory contains **shared AI agent resources** that are not tied to any specific coding tool.
The same rules, skills and connectors work with Claude Code, Kiro, Cursor, GitHub Copilot,
Antigravity, or any other agent that can read markdown and execute shell commands.

Three kinds of thing live here, and the distinction matters:

| | What it is | Delivered by |
| --- | --- | --- |
| [`rules/`](./rules/README.md) | Standing conventions — how we branch, commit, style code, treat environments | A pointer file per agent (`AGENTS.md`, `CLAUDE.md`, …) → [`CONTRIBUTING.md`](../CONTRIBUTING.md) |
| [`skills/`](./skills/README.md) | Procedures for multi-step jobs — review an MR, cut a release, fix a vulnerability | A thin wrapper per agent, generated by `yarn skills:sync` |
| [`connectors/`](./connectors/README.md) | Executable access to external services, run from the shell | Called by path from a skill, or by hand |

Rules always apply. A skill applies when its trigger matches. A connector is a tool either
one reaches for — and only one of four places executable functionality can live; which one a
new capability goes in is decided in
[Where executable functionality lives](#where-executable-functionality-lives).

The delivery lifecycle those pieces add up to — who owns which phase, what each hands off,
and where the specs and task one-pagers live — is documented in
[`docs/sdlc/`](../docs/sdlc/README.md). That split is deliberate: `.ai/` holds instructions
addressed to an agent, `docs/` holds knowledge addressed to the team.

## Rules and skills — one source, generated wrappers

Each agent reads its instructions from a different conventional path. Rather than maintaining
a copy per agent by hand, the per-agent files are **generated** from the canonical ones. The
third column is how the same agent gets the [MCP server's](../mcp/README.md) tools: a
project-scoped config committed to this repository where the client supports one, otherwise
a template to copy into the client's own settings.

| Tool               | Rules pointer                                | Skill wrapper                          | MCP config |
| ------------------ | -------------------------------------------- | -------------------------------------- | ---------- |
| *(any)*            | `AGENTS.md`                                  | —                                      | — |
| **Claude Code**    | `CLAUDE.md`                                  | `.claude/commands/<name>.md` → `/<name>` | [`.mcp.json`](../.mcp.json) |
| **Antigravity**    | `.agents/AGENTS.md`                          | `.agents/skills/<name>/SKILL.md`       | — ¹ |
| **GitHub Copilot** | `.github/copilot-instructions.md`            | `.github/skills/<name>/SKILL.md`       | [`.mcp.json`](../.mcp.json) ² |
| **Kiro**           | `.kiro/steering/00-workspace-rules.md`       | `.kiro/skills/<name>/SKILL.md`         | template: [`mcp/agent-configs/kiro.json`](../mcp/agent-configs/kiro.json) ³ |
| **Cursor**         | `.cursor/rules/workspace-rules.md`           | —                                      | [`.cursor/mcp.json`](../.cursor/mcp.json) |
| **Claude Desktop** | —                                            | —                                      | template: [`mcp/agent-configs/claude_desktop.json`](../mcp/agent-configs/claude_desktop.json) ⁴ |
| **Cline**          | —                                            | —                                      | template: [`mcp/agent-configs/cline.json`](../mcp/agent-configs/cline.json) ⁴ |

1. Antigravity's MCP documentation defines no workspace-folder variable and no rule for
   resolving a relative path, so nothing is committed for it. Add the server in its MCP
   settings with an absolute path, shaped like the Claude Desktop template.
2. In VS Code. It reads the portable `.mcp.json` at the workspace root as well as its own
   `.vscode/mcp.json`, and its documentation prefers the portable file for new servers, so
   one file serves both Claude Code and Copilot.
3. Kiro reads a workspace `.kiro/settings/mcp.json`, but its documentation defines neither a
   workspace-folder variable nor how a relative path resolves, so the repository ships a
   template with an absolute path rather than a committed file that might not start.
4. Configured outside the repository, so an absolute path is the only form that works.

The committed configs start a process on your machine — review them like any other
automation: [Security: automation is code execution](../docs/guides/workspace-automation.md#security-automation-is-code-execution).

```bash
yarn rules:sync      # regenerate the rule pointers
yarn skills:sync     # regenerate the skill wrappers from canonical frontmatter
yarn agents:check    # verify nothing has drifted — use in CI
```

**Do not hand-edit a generated file.** Hand-copied wrappers drift, and the drift is invisible:
before the generator existed, the same skill was named `Debug & Report` in one wrapper and
`debug-and-report` in another, with different descriptions — so it *triggered differently
depending on which agent you asked*.

The canonical source of truth always lives here in `.ai/rules/` and `.ai/skills/`.

## Where executable functionality lives

**This section is the placement rule for anything an agent executes.** Every other file in the
workspace that touches the question links here rather than restating it.

An agent reaches executable functionality in one of four ways. They differ in reach, in where
their credentials come from, and in what they cost the agent's context — so where a new
capability goes is a decision, not a habit.

| Kind | What it is | How the agent reaches it | Credentials | Put it here when |
| --- | --- | --- | --- | --- |
| **MCP tool** | A tool registered by the workspace server in [`mcp/`](../mcp/README.md) | Auto-discovered — the agent's client starts the server from its [MCP config](#rules-and-skills--one-source-generated-wrappers) and lists the tools | Root `.env` | It is needed across workflows, or by an agent with no skill running, and benefits from being always available |
| **Connector** | A repo-local script in [`connectors/`](./connectors/README.md) | By path: `node .ai/connectors/<service>/<script>.mjs` | Root `.env` | It is a skill-specific integration, a one-off, or the **CLI face of an MCP capability** that a person also needs from a terminal |
| **Skill-local script** | A script in `.ai/skills/<skill>/scripts/` — today in [`release-mr`](./skills/release-mr/SKILL.md) and [`fix-security-vulnerabilities`](./skills/fix-security-vulnerabilities/SKILL.md) | From inside that skill: `node .ai/skills/<skill>/scripts/<script>.mjs` | None today; root `.env` if one ever needs a secret | It is a mechanical step belonging to exactly one skill, and would never be run outside it |
| **Third-party CLI** | A tool that already exists — `git` throughout; `kubectl` / `kustomize` in `release-mr`; `yarn audit` / `npm audit` in `fix-security-vulnerabilities` | The CLI's own invocation | The tool's own auth — git credentials, kubeconfig, registry token | The tool already does the job and wrapping it adds nothing. The rules decide which of these the agent runs itself and which it hands over: [`local-environment.md`](./rules/local-environment.md) and [`git-workflow.md`](./rules/git-workflow.md) |

The MCP server and the connectors read the same root `.env` (template:
[`example.env`](../example.env)), so there is one place to rotate a token whichever form a
capability takes.

### One capability, two faces

`trace-id` is the instructive case of a capability that legitimately lives in two places. The
reconstruction engine exists once, in [`mcp/src/grafana/trace/`](../mcp/src/grafana/trace/). The
`grafana_trace_id` MCP tool calls it, and
[`connectors/grafana/trace-id.mjs`](./connectors/grafana/README.md) imports it — rather than
shelling out to the server or duplicating the logic. The agent gets it as a tool, a person gets
it as a CLI, and the two forms cannot disagree about what a trace means.

That is the only acceptable shape for a connector that mirrors an MCP tool: a second face on
one engine, never a second implementation.

### What each one costs the agent

- **An MCP tool costs context on every turn.** Every active tool's schema is sent to the model
  on every turn, so the cost of an MCP tool is paid whether or not it is used. That is an
  argument for tight descriptions and for not registering near-duplicates — not for a ceiling
  on the number of tools. How to write one that earns its place:
  [Adding a tool](../mcp/README.md#adding-a-tool).
- **A connector costs context at discovery.** Before it can call one, the agent lists
  directories, reads a README and builds a shell command — each step spends context, and each
  is a chance to get a flag wrong. That is why a connector is reached from a skill that names
  it, and why a capability the agent needs with no skill running belongs in MCP.
- **A skill-local script or a third-party CLI costs only what the skill spends on it**, because
  the skill names it at the step that uses it.

## Adding a New Skill

1. Create `.ai/skills/<skill-name>/SKILL.md` with `name` and `description` frontmatter — the
   description is the trigger, so write concrete phrasings the user would actually say.
2. Run `yarn skills:sync` to generate the four wrappers.
3. Add a row to [`.ai/skills/README.md`](./skills/README.md) and to
   [`CONTRIBUTING.md`](../CONTRIBUTING.md).

## Adding a New Rule

1. Create `.ai/rules/<topic>.md`.
2. List it in [`.ai/rules/README.md`](./rules/README.md), in the ordered list at the top of
   `scripts/sync-agent-rules.mjs`, and in [`CONTRIBUTING.md`](../CONTRIBUTING.md).
3. Run `yarn rules:sync`.

## Adding a New Connector

Only when the [placement rule](#where-executable-functionality-lives) says so.

1. Create `.ai/connectors/<service>/` with your `.mjs` scripts, following the
   [output contract](./connectors/README.md#output-contract).
2. Add the variables to [`example.env`](../example.env).
3. Add a row to the [register](./connectors/README.md#the-register), naming the skill that
   calls it, and add the directory to the structure above.
